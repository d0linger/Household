## Workflow

Choose a plan and a seven-day window. Desktop shows seven dated columns; mobile shows a chronological agenda of the same data. Day and meal-slot headings remain explicit. Every action has keyboard controls; optional drag/drop uses the same reviewed move operation. Empty slots offer a meal draft. Preserve drafts across refresh, failed requests and conflict review.

A meal has a date, slot, exact positive servings, title, notes, an explicit kind (recipe, free plan, leftovers, eating out or ordered food) and status (open, planned, purchased, cooked or cancelled). These are planning declarations; marking cooked does not invent a cooking record or consume stock. Non-recipe kinds and cancelled/completed meals produce no new recipe shopping demand. A status transition shows its effects before committing.

Recipe meals contain up to ten components with independent portions. Choosing a recipe loads a bounded preview including preparation/cooking effort. The user confirms the selected immutable version. A stored plan snapshot preserves the recipe's ingredients, instructions and base portions. A later live-recipe edit is offered for comparison and explicit replacement; it never silently rewrites an existing plan. Removed or disabled source modules do not erase a previously copied snapshot owned by the plan. New source selection and version comparison require current source authorization.

Move a meal to another date/slot or atomically exchange two meals within the same plan. Compare the versions of both meals and plan scope. Selected dates must remain in the plan interval; stale or missing records produce a named conflict. Optional drag/drop is an enhancement to these controls. Cancelled or cooked meals cannot silently become future planned meals through a move.

Copy a plan/template into a new seven-day range through a review. The copy receives new IDs, dates, component identities and open planning state. It preserves source snapshot provenance but copies no cooking result, purchase receipt, reservation or mutable core link belonging to the source meal. A repeated operation with the same request key returns the one new plan. Existing general CRUD remains compatible with the workspace or explicitly rejects edits that would invalidate its component contract.

Copied plans retain an immutable source-plan UUID, actor-scoped copy key and 32-byte request hash. Their unique tuple keeps a matching replay once-only after generic receipts expire, without changing the source plan merely because it was copied. Different details under the same copy key conflict. The source UUID is provenance without a restrictive source-plan FK, so the copy remains independent.

Daily effort totals add component preparation/cooking minutes sequentially by default and show unknown values separately. Parallel preparation is only considered when a user explicitly chooses it; it cannot be inferred from overlapping slots. Week reads return bounded meals and components with versions in a fixed number of queries, without per-ingredient lookups or eager images. Large plans use explicit time-window pagination and limits, not silent truncation.

Existing recipe time fields default to zero, so they cannot distinguish missing data from an explicitly known zero. Component review therefore uses nullable preparation/cooking minutes: positive source values can be shown as recipe estimates; a source zero stays unspecified until explicitly confirmed. Effort is counted once per component, independent of portion scaling.

## Persistence and integration boundaries to review

Keep mealplan tables independent of optional module schemas. Recipe selection must pass through the existing core integration boundary: validate household/source generation, lock the selected live parent/version and copy the confirmed immutable bundle into a mealplan-owned component snapshot. Use core.resource_links for optional navigable live references; no cross-module recipe FK. Local component snapshots and exact source version/generation/revision provenance survive recipe purge; current live links may disappear. A plan copied before an expansion must remain intelligible.

Plan/meal/component writes need shared lock ordering across the new workspace and existing generic actions/imports. Protect date bounds, maximum counts, whole-component identity, immutable source fields and parent version advancement. Lock both meals in stable order for swaps. Recipe source locks must fail clearly rather than invert another mutation's lock order. Core audit policies redact human recipe/meal content while retaining safe state/date/version changes.

The existing meal-to-recipe action and plan-to-shopping integration must use or preserve this snapshot contract. Repeating shopping generation and differential ingredient demand are separate MP14/17 work; the current slice must avoid making those paths silently ignore components, consume cancelled meals or follow changed live recipes. Define a safe interim compatibility path during the database review, then add meaningful tests for every retained entry point.

## Decisions following database review

Use one component table and extensions to existing plans/meals. Source UUID/generation/revision and snapshot are immutable; replacing a source creates a new component identity. The dedicated workspace locks the plan first and children in UUID order with NOWAIT. Narrow parent guards protect legacy child-first writes without waiting in an inverted order. Existing meals cannot change plan through generic CRUD. Any component mutation advances meal and plan versions; read final versions after child effects.

Week windows are exactly seven calendar days with at most 42 meals and ten components per meal. Component snapshots are limited to 1 MiB, complete meal snapshots to 2 MiB and a copied seven-day selection to 16 MiB. Week reads carry metadata only; a full component snapshot is loaded separately. Oversized selections produce named errors instead of truncation. Existing large plans remain stored and are accessed through bounded windows. The source review must show these limits before confirming a copied recipe.

After locking the plan, copy and shopping select at most 43 meal identities and lock them in UUID order with NOWAIT. The sentinel rejects oversized legacy windows before component locks. Component identities come only from bounded metadata: at most ten for a meal or 420 for a week. Locks never skip contested rows. The parent's trigger contract protects the interval between metadata reads and component locks; a child writer already in progress produces a conflict. Existing oversized legacy windows remain available through individual records and must be divided before workspace copy/transfer.

Conflict review names all replaceable fields in both drafts: date, slot, kind, status, meal portions, notes and ordered component portions, source revisions and nullable effort. Continuing a draft updates expected versions only after explicit review. Component reordering restores focus to an enabled control on the same component. Unknown request outcomes freeze mutation controls and retain the exact body/key for recovery. A known rejected copy keeps its dialog fields intact.

Legacy live-linked meals remain explicit unreviewed recipe drafts with their title, notes and reference. Migration does not invent a historical recipe selection or reveal a disabled source. Shopping transfer names any eligible recipe meal lacking reviewed components. Only open/planned recipe meals contribute; purchased/cooked/cancelled and non-recipe kinds do not. Transfers use the plan's own snapshots and bind only shopping generation. All components and exact, representable ingredient quantities are validated before the first shopping write. Older generic single-recipe callers without a reviewed source version are directed to the workspace.

Module purge may remove live navigation links but never the independent mealplan snapshot. Copies have new identities, open status and no inherited core links or completion data. Source comparison and fresh selection require current source authorization and generation. Existing idempotency records keep their original target metadata; new snapshot transfers use only shopping. Their original replay semantics must remain tested across source disable/purge.

Saving a newly selected recipe validates its current source generation and locks the live parent before copying. Recipe selection is a read dependency, so the committed planning response belongs only to mealplan: replay checks the current actor, household and mealplan generation before returning the original response, without re-opening a disabled or purged source. Its receipt has no recipe destination-generation dependency. This protects recovery from a lost response after the copy already committed. A fresh copy still requires current source authorization; an expired receipt cannot create a duplicate because the original plan version has advanced.

## Acceptance

Unit: date-window mapping, exact portions and effort totals with unknown values, allowed transitions and bounded snapshot normalization. PostgreSQL: source/household/generation guards, populated upgrade, generic-path compatibility, atomic move/swap/copy, concurrent writes, read bounds, immutable provenance, source disable/purge and rollback/audit behavior. Browser: create/choose recipes, move/swap with keyboard, mobile agenda, type/status decisions, copied week, named conflicts and preserved drafts, accessible components and dark/light views. Regression includes restore of copied snapshots and existing shopping/recipe behavior.
