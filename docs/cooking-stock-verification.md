The receipt names frozen product/location/lot labels, actual decisions and current reversal state, with links to each lot's existing Pantry correction flow and the Pantry-owned receipt. Partial/full reversal is derived from journal counter-movements; full reversal does not reopen the original source. Unavailable target details have a bounded already-completed explanation. |

## Durable proof, purge and recovery evidence

The [Core migration](../internal/database/migrations/core/000016_cooking_stock_postings.up.sql) retains an immutable minimal proof keyed by **household, Recipes generation and cooking-record UUID**. Actor and Pantry generation are excluded from that source uniqueness key. The proof stores identifiers/hash/counts/mode, not recipe notes or product names, and has no optional-module foreign key. Pantry owns the receipt and local movement details. Matching authorized replay returns the prior completion without new effects; changed reviewed values conflict. Current target module/generation controls detail visibility.

The [focused integration contracts](../internal/web/cooking_stock_integration_test.go) distinguish the lifecycle cases. After actual **Recipes purge**, the Pantry-owned receipt remains readable and its existing journal movement can be reversed; the Core proof remains. After **Pantry disable/purge**, replay retains the proof identity but redacts local details. Re-enabling a new Pantry generation does not reopen the completed cooking source or recreate stock. Deleting generic request receipts and reversing a movement also do not clear the durable source key. These contracts do not authorize old movements to be reversed into a new target generation.
