## Shared decisions

All new categories are off for external delivery by default, at both account and device level. Existing shopping watches and consent retain their established behavior while the schema-1 `shopping_notice` protocol remains supported. New producers use schema-1 intent references and a separate job kind `notification_push_v1`; the new wire protocol will be versioned separately so old cached service workers reject rather than misinterpret it. There is no historical replay: account `enabled_since`, device consent time, source event time and module activation generation all participate in eligibility. Reactivating consent establishes a new cutoff.

The compiled category registry defines chores_due (1h), chores_digest (4h), chores_escalation (1h), cooking_timer (60s), shopping/pantry/fuel/expenses/meters/documents (24h), mealplan (4h), security (1h) and test (60s). Timer/test attempts are limited to two; ordinary categories allow at most five within freshness. An intent has no title, amount, endpoint, HTML or URL. Generic localized templates belong to the client; references are resolved through authorized server routes.

An intent's dedupe key includes household, recipient, module generation, resource type/UUID, source revision, business occurrence and category. Moving a deadline requires a source revision change; retrying the same transaction cannot invent a new event. Jobs own leases; delivery rows will not introduce a second lease system. Cancel/revision checks are repeated at send time because already accepted provider messages cannot reliably be recalled.

Household remains portable Docker software: HOUSEHOLD_ORIGIN is installation configuration. No deployment domain is compiled into frontend/backend code. Each origin needs its own permission/subscription; moving to another origin requires explicit reconnection. Real Windows/Android/iOS devices are available according to the user, but no physical test has run. HTTPS reachability will be established for the actual test installation, not treated as a development-code prerequisite.

Changing the configured origin is not itself a subscription-revocation command. Before a domain move, disable sending and remove old device connections, then reconnect devices deliberately under the new origin. Existing registration envelopes bind account, household, session, authorization version, role and VAPID identity; they do not currently store the registration origin. The encrypted-envelope phase must make that distinction explicit in migration and operator guidance rather than implying an automatic origin fence already exists.

## Encryption migration contract (implemented; full acceptance in progress)

Keep encryption, CSRF, rate-limit and VAPID keys independent. Introduce a bounded keyring with one explicit active encryption key ID and retained read keys; reject duplicate IDs, malformed/short keys and a missing active key at startup. Versioned AES-GCM envelopes authenticate an unambiguous length-delimited context containing application, schema, purpose, household where applicable, account and immutable record ID. The key ID and envelope version are authenticated too. Generate a fresh cryptographic nonce on every write; never derive it from record IDs.

Legacy `household-v1` ciphertext remains readable only through its explicitly marked legacy path. Migration must not guess between formats or silently retry old AAD after a versioned authentication failure. TOTP, encrypted passkey credential/challenge records and push subscriptions have separate purpose contexts. Passkey private keys never leave authenticators. A resumable bounded re-encryption command compares original ciphertext/version before replacement, preserves semantic audit history and reports counts without plaintext. Retire an old read key only after a complete inventory and a verified encrypted backup/restore using synthetic TOTP/passkey/push data. VAPID rotation is separate and requires controlled reconnection, not ciphertext re-encryption.

Read-only preparation on10 November confirmed that the existing backup already stores actual CSRF, encryption and rate-limit keys in a private `security-keys.json` inside the encrypted restic snapshot. Preserve that recovery mechanism: extend and version the encrypted private bundle for retained read keys, while public manifests and evidence expose only identifiers and formats. Current restore verification checks schema readiness, projections and attachment bytes but does not yet prove protected-row decryptability. N49 must validate every restored encrypted credential/subscription using the snapshot's own bounded, strictly parsed key bundle before marking the backup verified; current live keys are not a substitute. Passkey challenge/credential row IDs must exist before new encryption, and retained readers must be recognized by both push delivery and housekeeping. These are implementation requirements, not completed checks.

Further read-only preparation: authentication writes do not all acquire the backup's household lock. Encryption-key inventory and `pg_dump` therefore need the same exported repeatable-read snapshot, with every referenced key present in the private escrow, rather than separate live reads. PostgreSQL requires importing that snapshot before the importing transaction's first query; the exporting transaction must remain open. See the [official snapshot contract](https://www.postgresql.org/docs/current/sql-set-transaction.html). Legacy AES material is the SHA-256 of the original configured secret string; decoding that string before deriving the legacy key would break existing records. The new independent crypto package should use standard-library [HKDF](https://pkg.go.dev/crypto/hkdf) for purpose separation and authenticated format/key/identity metadata, without trial decryption across keys.

Historical preparation contract (unimplemented when written; see the [current checkpoint](#current-checkpoint--10-november-2026) for implementation and acceptance): persist closed, personal event kinds within existing password, recovery-code, TOTP, passkey, session-revocation, administrative target-account and actual device-authorization transactions. An independent transaction-only package avoids an auth/store dependency cycle. Never turn anonymous login failures, no-op changes or routine connection refresh into broadcasts. Password recovery and account changes may invalidate every current push session: retain the personal inbox event for later legitimate login, while preserving revoked-session rejection and the no-history rule for newly registered devices. Passkey labels, IP addresses, tokens and arbitrary text do not belong in the event payload.

Core40 read-only review identifies a narrow metadata-only schema change across TOTP credentials, passkey credentials, encrypted passkey challenges and push subscriptions; existing ciphertext and semantic state remain untouched until explicit rotation. Challenge metadata must be mandatory only for the three encrypted passkey purposes, with explicit non-NULL checks, and NULL for other purposes. Existing TOTP/push audit policies stay installed; passkey/challenge semantic-only exclusions stay unchanged, so the expected audit-policy census remains165. Fuel's exact Core39 guards and associated authority hash must advance to40 only after matching their reviewed definitions; the dirty40 migration marker prevents using ordinary clean39 runtime readiness as a predecessor check.

Rotation should use the owner CLI, a dedicated connection holding a singleton advisory lock, bounded audited transactions and ciphertext/format/key-ID compare-and-swap. It must not change TOTP/passkey counters, challenge consumption or subscription consent. Retirement checking must not delete operator secret files: report the complete remaining-reference and verified-restore evidence, then document the explicit operator removal/restart. Encrypted backup escrow retains the keys required to restore historical snapshots. Missing retained keys are an operational failure, not permission for housekeeping to silently disable otherwise valid devices. These are reviewed Phase F requirements, not implementation or test results.

Phase F configuration decision: an optional `HOUSEHOLD_ENCRYPTION_KEYRING`/`_FILE` replaces, rather than supplements, `HOUSEHOLD_ENCRYPTION_KEY`/`_FILE`. The strict version1 document has one active ID, an optional explicit legacy ID and at most eight `{id,secret}` entries within32KiB. IDs use the existing push fingerprint, SHA-256 of `household-encryption-v1` followed by a NUL and the exact secret string; declared IDs must match their material. Reject duplicate JSON fields, unknown fields, duplicate IDs/material and trailing data. With no ring, preserve the existing single-secret installation as one active/legacy key. Omitting the legacy ID in an explicit ring disables legacy reads; never infer it from the active key. Use exact existing secret-string bytes for legacy derivation. New key generation uses32 cryptographically random bytes; accepting a legacy string's length is not proof of its entropy.

The independent crypto API uses a closed purpose set: TOTP, passkey credential, registration/login/reauthentication challenge, and push subscription. TOTP/passkeys bind the account without a mutable household membership; discoverable login challenges bind an explicitly absent account. Push binds household, account and subscription. Every version2 write authenticates its format, key ID and length-delimited immutable context. All protected writers, readers, housekeeping, rotation and encrypted backup/restore must adopt this contract together before acceptance; this paragraph records the decision, not completed implementation.
