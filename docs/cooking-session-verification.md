# Cooking session verification — 2026-10-25

This documentation pass covers **RE02, RE03, RE04 and RE10**. It compares [PRODUCT.md](../PRODUCT.md), [DESIGN.md](../DESIGN.md), the [cooking contract](cooking-session.md), `cooking.html`, `cooking.js`, shared CSS, the HTTP handler and cooking store code with the current screenshots and existing execution evidence. The incumbent Household design remains authoritative. Automatic Pantry consumption is outside this scope.

| Area | Checked implementation and interface evidence |
|---|---|
| Guided cooking | A personal session keeps an immutable recipe version, one current instruction, step progress and an ingredient checklist. Keyboard actions retain focus after persistence. Later recipe edits do not replace the selected source. Recipes without instructions direct the user back to authoring. |
| Portions | The store scales known quantities with exact rational arithmetic. Display rounding is marked with “≈”; tiny positive values use a threshold rather than apparent zero. Unknown amounts and descriptive hints remain visible. Portion changes affect the session, not the recipe. An unsubmitted portion draft survives an independent timer action. |
| Persistent timers | Named timers store a UTC deadline or paused milliseconds. PostgreSQL time is read after locking, and browser countdowns use that response plus a monotonic clock. The current browser run checks multiple timers, pause/resume, unchanged deadlines across reload, elapsed state, acknowledgement and reviewed restart/removal. Countdown outputs have live announcements disabled; a separate status announces named expiry. |
| Error recovery | An uncertain start freezes its form and offers an explicit retry with the same request key. A failed checklist write retains the local selection and blocks unrelated mutations until saved-state review. Concurrent changes and uncertain network failures require review; portion and completion drafts are preserved while unsaved progress may be replaced explicitly. |
| Confirmed history | Completion reviews actual servings, household-local date, optional rating and notes with initial focus on cancellation. Confirming stops remaining timers and creates one immutable household-readable result. The store checks authorization/generation before durable completion replay; changed completion details conflict. Abandoning creates no cooking result. |
| Boundaries | Parameterized session reads include household and user predicates; completed history is household-readable. Mutations use the existing session/module barriers and optimistic versions. Limits are ten open sessions per user, twenty stored timers per session and timer durations from one second to 24 hours. History uses twenty-row pages plus a sentinel. The HTTP operation has a 20-second context. |
