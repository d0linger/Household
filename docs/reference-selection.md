# Reference choices and shopping reads

`GET /api/v1/core/reference-options/{module}/{entity}` returns only `records: [{id,label}]` and `next_cursor`. A page contains at most 50 choices. Search uses literal case-insensitive substring matching, including literal percent signs; no SQL pattern syntax is exposed. Active household memberships have an explicit core allowlist. Disabled modules, archived shopping lists and items inside archived lists are excluded.

The cursor is signed with a domain-separated existing authentication HMAC. It binds household, user, module, entity, search and module generation, expires after 30 minutes, and uses immutable creation timestamp plus UUID as a deterministic tie-breaker. Requests have fresh authentication and module checks. This is keyset paging, not a frozen database snapshot: new rows appear on reload, deleted rows disappear. Updating a label does not move an existing row across the cursor. Old `/references/` array responses remain available for existing clients.

The form keeps its selected values when moving between result pages or changing the search. A loading or failed required, multiple, or selected optional choice blocks submission and offers retry without erasing inputs. Only an empty optional unavailable field can be omitted. A choice page replaces unselected options to bound DOM size. `GET /api/v1/core/reference-options/{module}/{entity}/{id}` names one scoped selection without scanning earlier pages; historical inactive household memberships can be named there but are excluded from new choices.

`GET /api/v1/shopping/lists/{id}/items` scopes every row to the authenticated household and selected list. It returns up to 100 items, a signed next cursor, the list, generation and whole-list total/completed counts. Search matches name, group, product and brand. The board cursor uses store aisle order, normalized group, item order, normalized name and ID; its signature also binds the selected store. Unlike reference choices, these sort keys can change during edits, so a refresh from the beginning is needed after concurrent reordering. The displayed progress always includes filtered-out rows. Each read is bounded; totals and page data can reflect adjacent committed states during concurrent edits and are refreshed subsequently. No repeatable snapshot is promised. The bounded cursor allows up to 8192 bytes to accommodate JSON-escaped valid names.

The shopping view polls every 15 seconds while visible and online, backs off to 120 seconds on failure, and cancels outstanding reads before writes. A refresh preserves quick-entry values, focused item links and the user's completed-section disclosure state. Shopping mode collapses entry and search controls while preserving their inputs. Check/uncheck and quick-add use the existing authorized, versioned, idempotent, audited mutation contracts. The next POST key is retained after a failed quick-add for an unchanged payload. Inputs changed during a slow POST survive its successful response; changed filters discard the old page cursor even while a write is running. Quantity parsing is a local suggestion using integer millionths; it only changes form fields after the user selects “Erkennung übernehmen”.

Conflicts show current server values and the user's intended values. `GET /api/v1/shopping/items/{id}` returns the household-scoped current item with exact quantity text and named variant, replacement and assignment for that comparison. A current unavailable item cannot be confirmed as checked. A confirmed retry uses the reviewed version and a new operation key; another concurrent change produces another conflict. Generic PATCH forms offer the same explicit comparison. No stale form is automatically submitted with a substituted version or generation.

New scripts are ordinary embedded local assets. These changes add neither external browser requests nor private service-worker caching. The initial six improvements required no schema change; the catalog extension adds shopping migration 2 and core migration 6, documented in shopping-catalog.md.
